# ReMCP tool reference

> Generated from the actual primary /mcp production tool catalog.

ReMCP publishes **174 individually defined MCP tools**: 83 runtime
operations and 11 account/fleet operations. Every tool has its own name,
closed input schema, output schema and operation-specific annotations. No grouped dispatcher
or optional widget-only tool is advertised on this production profile.

For visible interaction, use Accessibility/UI Automation, browser DOM/CDP, OCR and coordinates
in that fallback order. Verify state-changing operations using semantic reads and waits.

Required parameters are marked with an asterisk.

## Account & fleet

Each account query, pairing operation and device administration action is independently described and authorized.

| Tool | Safety | Parameters | When to use |
| --- | --- | --- | --- |
| `list_devices` | read-only | None | Use this when the target computer is not already unambiguous. Call it first to list computers paired to the signed-in ReMCP account and see which ones are online. |
| `who_am_i` | read-only | None | Use this when the person asks which ReMCP account they are signed in as, how many machines are paired and online, or how many tool calls they have made lately. |
| `create_pairing_command` | local state | None | Use this when the person wants to connect another computer to their ReMCP account, or asks how to add a device: returns platform-specific Windows/macOS/Linux commands, the pairing code, and when it expires. Windows uses the no-prerequisite PowerShell bootstrap; macOS/Linux use the npm launcher. The same commands are returned while the code is still valid. |
| `get_recent_tool_calls` | read-only | `limit` (number), `device` (string), `tool` (string) | Use this when you need to recover recent ReMCP activity or answer what was just done. It returns the most recent tool calls with the computer they ran on, success state and duration. |
| `get_usage_statistics` | read-only | `days` (number), `device` (string), `tool` (string) | Use this when the person asks for account-level historical ReMCP usage over days: call counts, success rate, average duration, and per-tool/per-device breakdowns. Use get_runtime_stats instead for counters from the current local runtime session on one machine. |
| `get_configuration` | read-only | None | Use this when the person asks how the hosted ReMCP deployment/account is configured: server version and endpoint, runtime release installed on devices, retention/telemetry policy, hosted limits, and paired-computer versions. Use get_runtime_info for one computer's local runtime roots, policy and limits; use get_system_info for that computer's OS/CPU/memory/disk state. |
| `ping_device` | read-only | `device*` (string) | Use this when you need to check that a paired computer answers right now and measure the round trip. The device agent answers the ping itself, so it works even while the local runtime is restarting or missing, and it reports hostname, platform, uptime and versions. |
| `rename_device` | local state | `device*` (string), `config_key*` (string), `value*` (string) | Use this when the user wants to change the account-visible label of one paired computer. Do not use set_config_value for renaming: that device tool changes local runtime preferences instead. Access roots, command guardrails and resource limits stay on the computer itself. |
| `enable_device` | local state | `device*` (string) | Use this when the user needs to enable an existing paired computer only when the user explicitly requests it. Changes that pairing to enabled; requires its device id. |
| `disable_device` | changes state | `device*` (string) | Use this when the user needs to disable an existing paired computer only when the user explicitly requests it. Disconnects the pairing until re-enabled; requires its device id. |
| `remove_device` | changes state | `device*` (string) | Use this when the user needs to permanently remove an existing paired computer only when the user explicitly requests that irreversible action. Revokes the pairing; requires its device id. |

## Files

Read, find, edit, transfer and manage files using separately named operations.

| Tool | Safety | Parameters | When to use |
| --- | --- | --- | --- |
| `read_file` | read-only | `path*` (string), `offset` (number), `length` (number), `device*` (string) | Use this when the task calls for plain text files on a paired computer: source code, configuration, Markdown, logs, scripts, or other line-oriented text. | `read_files` | read-only | `path` (string), `pattern` (string), `max_files` (number), `max_lines_per_file` (number), `include_ignored` (boolean), `device*` (string) | Use this when the exact file list is not already known and the user wants the contents of every file matching one glob under a directory. | `read_multiple_files` | read-only | `paths*` (array<string>), `device*` (string) | Use this when the user names two or more exact file paths to read in one call. Do not use it for glob discovery: use read_files instead. For one known path use read_file. |
| `read_binary` | read-only | `path*` (string), `offset_bytes` (number), `length_bytes` (number), `device*` (string) | Use this when the user needs a non-text file transferred or inspected byte for byte as base64 chunks. | `write_binary` | changes state | `path*` (string), `data*` (string), `mode` ("rewrite" \| "append"), `device*` (string) | Use this when the user needs base64 data written to a file on a paired computer byte for byte, including files too large for a single call. |
| `hash_file` | read-only | `path*` (string), `algorithm` ("sha256" \| "sha1" \| "md5"), `device*` (string) | Use this when the user wants a checksum to verify a download, compare two files, or confirm a transfer. |
| `list_directory` | read-only | `path*` (string), `depth` (number), `pattern` (string), `device*` (string) | Use this when the user wants to see what a directory on a paired computer contains, optionally filtered by a glob. |
| `get_file_info` | read-only | `path*` (string), `device*` (string) | Use this when the user needs the size, type, permissions, or modification time of one file or directory before deciding what to do with it. |
| `write_file` | changes state | `path*` (string), `content*` (string), `mode` ("rewrite" \| "append"), `device*` (string) | Use this when the user asks to create or replace the complete contents of exactly one text file. | `write_files` | changes state | `files*` (array<object>), `device*` (string) | Use this when the user asks to create or replace the complete contents of two or more independent text files in one batch. | `apply_patch` | changes state | `patch*` (string), `path` (string), `dry_run` (boolean), `device*` (string) | Use this when you already have a unified diff with one or more hunks and want to apply it to one or several files. Do not use write_file for the same patch-shaped change, and prefer edit_block when the change is one exact text block rather than a diff. |
| `set_permissions` | changes state | `path*` (string), `mode*` (string), `recursive` (boolean), `uid` (number), `gid` (number), `device*` (string) | Use this when the user asks to change mode bits or ownership of a file or directory, for example to make a script executable. |
| `edit_block` | changes state | `file_path*` (string), `old_string*` (string), `new_string*` (string), `expected_replacements` (number), `allow_fuzzy` (boolean), `dry_run` (boolean), `device*` (string) | Use this when one known text block in one file should be replaced, with a whitespace-tolerant fallback and optional dry-run diff. Use write_file only when replacing the whole file, and replace_lines when the intended target is a known line range rather than matching text. |
| `replace_lines` | changes state | `path*` (string), `start_line*` (number), `end_line*` (number), `content*` (string), `dry_run` (boolean), `device*` (string) | Use this when the intended edit target is a specific 1-based line range in one file, optionally as a dry run. | `replace_in_files` | changes state | `path*` (string), `pattern*` (string), `replacement*` (string), `filePattern` (string), `regex` (boolean), `dry_run` (boolean), `maxFiles` (number), `device*` (string) | Use this when the same text or regular-expression replacement should be searched and applied across multiple files under a path, such as a rename or version bump. | `diff_files` | read-only | `left*` (string), `right*` (string), `context_lines` (number), `device*` (string) | Use this when the user wants to see how two text files differ, before or after a change. |
| `move_to_trash` | changes state | `source*` (string), `device*` (string) | Use this when the user wants a file or directory removed but still recoverable from the system trash. |
| `create_directory` | local state | `path` (string), `paths` (array<string>), `device*` (string) | Use this when the user asks to create a directory, including any missing parent directories. |
| `move_file` | changes state | `source*` (string), `destination*` (string), `overwrite` (boolean), `device*` (string) | Use this when the user asks to move or rename exactly one file or directory from one source to one destination. For two or more moves use move_paths. |
| `copy_file` | changes state | `source*` (string), `destination*` (string), `overwrite` (boolean), `device*` (string) | Use this when the user asks to copy exactly one regular file to a new path on the same computer. For directories or two or more copies use copy_paths. |
| `copy_paths` | changes state | `paths*` (array<object>), `overwrite` (boolean), `device*` (string) | Use this when the user asks to copy a directory recursively or two or more paths in one request. For exactly one regular file use copy_file. |
| `move_paths` | changes state | `paths*` (array<object>), `overwrite` (boolean), `device*` (string) | Use this when the user asks to move or rename two or more files/directories in one batch. For one source/destination pair use move_file. |
| `delete_path` | changes state | `path*` (string), `recursive` (boolean), `device*` (string) | Use this when the user explicitly asks to remove exactly one file or directory and does not need it recoverable. Use delete_paths for two or more targets, or move_to_trash when reversibility matters. |
| `delete_paths` | changes state | `paths*` (array<string>), `recursive` (boolean), `device*` (string) | Use this when the user explicitly asks to remove two or more named files or directories in one batch. For one target use delete_path; use move_to_trash when reversibility matters. |
| `create_archive` | changes state | `paths*` (array<string>), `destination*` (string), `format` ("tar" \| "tar.gz" \| "zip"), `device*` (string) | Use this when the user wants files or a directory packed into a tar, tar.gz, or zip archive, for example before a transfer or a backup. |
| `extract_archive` | changes state | `archive*` (string), `destination` (string), `device*` (string) | Use this when the user wants an existing tar or zip archive unpacked on a paired computer. |
| `start_search` | local state | `path*` (string), `pattern*` (string), `searchType` ("content" \| "files"), `filePattern` (string), `ignoreCase` (boolean), `maxResults` (number), `includeHidden` (boolean), `includeIgnored` (boolean), `contextLines` (number), `literalSearch` (boolean), `device*` (string) | Use this when the user wants to find filenames or perform a content search under a path and does not need every matching file read in full. | `get_more_search_results` | read-only | `sessionId*` (string), `offset` (number), `length` (number), `device*` (string) | Use this when a search started with start_search still has more matches to return. |
| `stop_search` | local state | `sessionId*` (string), `device*` (string) | Use this when a search session is no longer needed and should release its resources. |
| `list_searches` | read-only | `device*` (string) | Use this when you need to know which search sessions are still active on a machine. |

## Terminal

Start, monitor, interact with and terminate sessions using independent process tools.

| Tool | Safety | Parameters | When to use |
| --- | --- | --- | --- |
| `start_process` | changes state, open-world | `command*` (string), `timeout_ms` (number), `device*` (string) | Use this when the user asks to run a shell command, build, test suite, script, or terminal server that is not already covered by a narrower semantic tool. Prefer launch_app for GUI applications, service for service-manager operations, power_action for lock/sleep/restart/shutdown, network for routine network inspection/tests, event_log for OS logs, installed_apps for software inventory, environment for environment facts, and open_path/reveal_path for opening or revealing files. |
| `read_process_output` | read-only | `pid*` (number), `offset` (number), `length` (number), `timeout_ms` (number), `device*` (string) | Use this when a process started earlier has more output to show and you do not want to wait for a pattern. |
| `interact_with_process` | changes state, open-world | `pid*` (number), `input*` (string), `timeout_ms` (number), `device*` (string) | Use this when a running process is waiting for input, such as a prompt or a confirmation. |
| `wait_for_process_output` | read-only | `pid*` (number), `pattern*` (string), `timeout_ms` (number), `device*` (string) | Use this when you need to wait until a running command prints something specific, such as a readiness line or a failing test name. |
| `force_terminate` | changes state | `pid*` (number), `device*` (string) | Use this when a process session created by start_process must stop, such as a runaway build or server left behind. For an arbitrary operating-system PID that is not a ReMCP terminal session, use kill_process instead. |
| `list_sessions` | read-only | `device*` (string) | Use this when you need to know which ReMCP terminal sessions created by start_process are still running. Use list_processes for the computer-wide operating-system process list. |

## Contract notes

- Every public tool has a human-readable title/description, explicit input schema, output schema for structured results, and MCP safety annotations in the production catalog.
- Structured tool calls return `structuredContent` that matches the advertised output schema together with normal MCP content where useful to the model.
- Browser/CDP tools are capability-aware and can be enabled or disabled as the local runtime discovers or loses a usable loopback browser endpoint.
- `computer_snapshot` is the broad first-look tool for an unfamiliar desktop; once the target is known, prefer the narrowest dedicated tool for the action and verify with semantic state before using pixels.
- The website renders this same catalog at [remcp.site/docs#tools](https://remcp.site/docs#tools).
